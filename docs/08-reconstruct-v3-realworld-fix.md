## 1. 怎么测出真机数据的

真机的 Word / PDF 里带着**带坐标的文字层**，可以用 `PDFPage.characterBounds(at:)` 逐字符取矩形，
再按 y 聚成行 —— 这就把真机 Vision 的 `[(text, bbox)]` 完整还原出来了。

工具：`/tmp/pdfdump/ocr.swift`（macOS 命令行，PDFKit）。可复用，建议收进 `Tools/`。

> ⚠️ 第一个坑：按 y 聚类**不能用「与上一个字符比较」的链式写法**，逐字符漂移会累积，
> 把好几行粘成一行，解出来是 `SrsSe., aonnes ua Iboip_e` 这种乱码。
> 必须**与本行首字符比较**硬切。

### 2.3 最要命的一条：真机 OCR 行是错的

反解出的营养表真机 OCR（视觉行从上到下）：

```
项目每100克NRV%        ← 一整行，3 个单元格被合并
能量1429千焦
17%蛋白                ← 「17%」属于能量行，「蛋白」属于蛋白质行，跨行粘一起
质1.5克3%脂肪0.8       ← 横跨两个视觉行
克碳水化
合物8.8克2
7%
```

对照 fixture（同一张印刷品、摆正拍）：

```
[15] 项目      [16] 每 100克   [17] NRV%
[18] 能量      [19] 1429 千焦  [20] 17%
[21] 蛋白质    [22] 1.5克      [23] 3%
...
```

**同一个表，fixture 是 18 个独立 cell，真机只剩 7 个错位行。**
而且真机表格的 x 范围只有 `0.082 ~ 0.25`，占页面宽度 **17%**；fixture 上是 `0.147 ~ 0.84`，占 **70%**。

## 3. 根因链（按影响排序）

### R1 · OCR 跑在**未矫正的原图**上 —— 第一根因 🔴

`PageFileStore.commit()` 里：

- `.original` = 相机直出，**未透视矫正、未去阴影、未裁边**
- `.rendered` = 透视矫正 + 增强后的图

而 `ReconstructViewModel.reconstruct()` 原来写的是：

```swift
if fileExists(original), let parsed = await parse(url: original, ...) {
    pages.append(parsed); continue   // ← 原图一存在，永远轮不到 rendered
}
```

一条 `continue` 把所有后处理算法全废了。OCR 吃的是倾斜、带阴影、带 UI 边框的原图，
于是 §2.3 的行错位、字符误识（`Lemice` / `Ahorthe` / `JWCe` / `CAKSS`）、构图偏移**同时发生**。

**一个反直觉的副作用**：关掉「保留原图」开关，还原效果反而变好 —— 因为那样 original 不存在，
才会落到 rendered 分支。这是这个 bug 的指纹。

> ✅ 已修：改成 rendered 优先、original 兜底，且不做存在性检查（交给 `parse` 自己失败）。

### R2 · 单张 fixture 过拟合 🔴

M0~M2 的所有阈值都是拿 `docs/fixtures/images/*.jpg` 这两张**摆正、干净**的图调出来的：

| 阈值 | fixture 值 | 真机值 | 结果 |
|---|---|---|---|
| 表格 x 跨度 | 0.147~0.84 | 0.082~0.25 | 列聚类全废 |
| 单元格粒度 | 每 cell 一行 | 整行合并 | 列聚类只剩 1 列 |
| 「营养成分表」 | 完整一行 | 识别成「◎配料：…」+ 孤立「表」 | **anchor 找不到** |

**测试全绿 ≠ 真机能用**。这是 M0 立 fixture 时就想避免的坑，结果还是踩了 ——
因为 fixture 只有「理想图」一档，没有「真机烂图」这一档。

### R3 · 表格检测 anchor 强依赖，无降级阶梯 🟠

```swift
guard let titleAnchor else { return nil }   // 无锚点直接放弃
```

真机上「营养成分表」没被识别出来 → 这一行直接 return nil → **整张表消失**。
后面 v1 兜底也失败（v1 依赖同样的 cell 粒度假设），于是彻底没有 `w:tbl`。

**单点失败即全盘失败**，没有任何 graceful degradation。

### R4 · 没有 OCR 噪声过滤 🟠

状态栏、App 导航栏、底部工具栏、二维码 URL 全部当正文导出。
扫描王类产品会先做「文档区域分割」，把非文档内容挡在外面。

### R5 · Figure 检测把**整块文字区**当配图 🟠

v1 把「题目 → 下一题」的整块 gap 直接交出去，裁出 844×393、768×1005 的满屏文字截图。
**比 0 个 figure 更糟** —— 用户看到的是一堆「文字的照片」。

### R6 · A/B/C 切换无反应（用户报的 bug）🟡

`docxURL` 一旦导出就不为 nil，导出按钮变成 `ShareLink`，切档后点击直接分享**旧文件**。

## 5. 优化方案（v3 路线图）

### P0 · 图像层 —— 决定上限，必须先做

| 任务 | 说明 | 优先级 |
|---|---|---|
| **P0-1** | 还原链路吃 rendered（✅ 已修） | 已完成 |
| **P0-2** | **OCR 专用预处理档**：与展示用的 rendered 分开。强制 去阴影 → 局部对比度 → 轻度锐化 → 灰度。用户选了「原图」滤镜时也要走这档 | P0 |
| **P0-3** | **重 OCR 机制**：若 `reconstruct` 时发现 rendered 的 OCR 质量分低于阈值（行数 < 预期 / 平均 confidence 低），自动用预处理档重跑一次 | P0 |
| **P0-4** | **文档区域二次分割**：用 `VNDetectDocumentSegmentationRequest` 再切一次，挡掉截图场景的状态栏 / UI chrome（比 R4 的启发式更根本） | P1 |

> P0-2/P0-3 是和扫描王拉开差距的关键。扫描王的 OCR 永远是跑在「去阴影 + 二值化」后的图上，
> 不是跑在「好看」的图上 —— 这两件事要解耦。

### P1 · 检测层 —— 去过拟合，加降级阶梯

| 任务 | 说明 |
|---|---|
| **P1-1** | **表格检测降级阶梯**：`title anchor` → `通用数字列检测`（≥3 行 × ≥2 列 + 数字密度）→ `v1 兜底`。任何一级成功就出表，不再全盘放弃 |
| **P1-2** | **列切分改用 x 投影找 gutter**，不再依赖「每 cell 一个 OCR line」的假设（该假设在真机已证伪） |
| **P1-3** | **行切分同理**：y 投影 + 自适应阈值，容忍倾斜 |
| **P1-4** | **OCR 行修复**：检测「跨行粘连」（如 `17%蛋白`），按 x 位置拆分回正确行 |
| **P1-5** | **多尺度重试**：列聚类失败时，用不同 gutter 宽度重试 N 次取最优 |

### P2 · 导出层

| 任务 | 说明 |
|---|---|
| **P2-1** | A 档表格补 `w:tblPr` 样式（边框、表头底纹），现在只有裸 `w:tbl` |
| **P2-2** | 表格 cell 对齐：数值列右对齐、表头加粗 |
| **P2-3** | B/C 档目前没有真实用户价值验证，建议先隐藏，等 A 档稳定再放出来 |
| **P2-4** | PDF 文字层按 block 顺序写，避免 PDFKit 读出来乱序 |

### P3 · 闭环 —— 防止再犯 R2

| 任务 | 说明 |
|---|---|
| **P3-1** 🔴 | **建「真机烂图」fixture 档**：把本次反解出的真机 OCR 固化成 `ReconstructV2Fixtures.workbookRealDevice` / `nutritionRealDevice`，测试必须在**理想图 + 真机图**两档上都过 |
| **P3-2** | **端到端断言**：从图片 → parse → docx，断言 `w:tbl > 0`。现在只有单元级断言，链路断了测试照样绿 |
| **P3-3** | App 内加「诊断导出」：一键导出 OCR 的 `[(text,bbox)]` JSON，下次真机出问题直接拿数据，不用再逆向 PDF |
| **P3-4** | `Tools/pdfdump` 收进仓库，形成「导出 → 反解 → 固化为 fixture → 修 → 回归」的标准流程 |

> **P3-1 是本轮最重要的教训。** 没有它，R2 还会以别的形式再来一次。

## 6. 与扫描王的差距：诚实评估

| 维度 | 扫描王 | 纸匣现状 | 差距性质 |
|---|---|---|---|
| 图像预处理 | 自动裁边 + 去阴影 + 二值化 + 锐化 | 有透视矫正，但**还原链路没吃它**（R1） | **工程 bug，可立即追平** |
| OCR 引擎 | 自研/定制 + 云兜底 | Apple Vision（端侧） | 端侧差一档，**需云通路才能追平** |
| 版面分析 | 深度学习版面模型 | 纯几何启发式 | **架构差距，需 Core ML 版面模型** |
| 表格还原 | 深度学习表格结构识别 | 几何聚类（依赖 cell 粒度假设） | **架构差距** |
| 手写/勾选 | 专门模型 | 无 | 缺能力 |

**现实判断**：P0 + P1 做完，能把「完全不可用」拉到「印刷体文档基本可用」。
要真正追平扫描王，必须有 **云通路（TextIn / Azure DI）+ 版面模型**，纯端侧几何算法有天花板。

建议**尽快把云通路接通**（`TextInDocumentParser` 已存在但未配置 key），
端侧作为离线 / 隐私场景的降级方案，而不是主方案。

## 8. 一句话总结

> 不是算法不够好，是**喂给算法的图就是错的**。
> R1 那条 `continue` 让整条还原链路一直在给一张未矫正的原图打补丁。
> 修完图像层，再谈算法；同时把真机数据固化进测试，否则下次还会重演。
